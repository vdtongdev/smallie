Short-term, long-term (knowledge graph) and cross-chat memory.

**Memory:**
- Short-term: checkpointer, per conversation.
- Long-term: a knowledge graph per user (`app/core/graph.py`) in plain tables `graph_nodes` (kind `user`/`file`/`entity`/`agent`/`note`; file nodes carry `document_id`, entities and notes an `embedding`) and `graph_edges` (`relation`, provenance `source` = `chat`/`document`/`import`, `document_id`, `conversation_id` without FK), both `user_id`-scoped with ON DELETE CASCADE; laid out as vertex + edge tables so a PostgreSQL 20 `CREATE PROPERTY GRAPH` can sit on top (SQL/PGQ was pulled from PG 19). Only facts touching the User node or a file node are kept. Agent notes use two relations: `agent -[noted]-> note` (this agent learned the note; one `agent` node per user and route) and `note -[about]-> entity / file / User` (what it mentions). A note's `norm` is `<route>:<normalized text>`, so two agents never share a note node. Agents never save facts themselves (free models skipped the optional save call, AP-006): after every finished turn with an answer (paused turns are skipped), the `remember_turn` background task runs `extract_facts(..., agent=...)`, where `agent` is `MESSAGE_ROUTES.get(_answered_by(messages))` (`app/orchestration/orchestrator.py`); one call of the orchestrator's model through `ask_structured` (`FactUpdate`, `EXTRACT_PROMPT`; a `None` with no tool call saves nothing and returns 0; the user's file names, the relations already present and the answering agent go in the human message). Pydantic is the filter (snake_case relation, ≤ 8 triples; `FactUpdate.notes`: `AgentNote` with `text` ≤ `NOTE_CHARS` 200 and `about` defaulting to empty, first `MAX_NOTES` 3 kept). With no route the notes are dropped and the facts are kept. Its tokens go into the usage totals. `save_facts` resolves names: user words → the User node, a file name → its file node, else an entity by exact `normalize`d name, then nearest embedding ≥ `SAME_ENTITY` (measured; re-measure after changing the embedding model), else a new node; a relation in `FUNCTIONAL` replaces the user's old edge; orphan entities are dropped. When the agent is named, `extract_from_turns` lists that agent's current notes in the human message, numbered from 1, newest first (`current_notes`, the same ones `recall_notes` shows, at most `RECALL_NOTES`), and passes their node ids to `save_notes(user_id, agent, notes, conversation_id, current=...)` (run through `asyncio.to_thread`). Each `AgentNote` has `replaces` (optional number; a bad value becomes None and never fails the reply). `save_notes` saves under the answering agent's route and matches each note in order: the note with the same `norm`; else the note named by `replaces` when it is this agent's note for this user; else the nearest note of that agent at cosine similarity ≥ `SAME_NOTE`; else a new note node. A matched note is updated in place with its `about` edges replaced (newest wins). When `replaces` names a different note than the same-`norm` one, the named note's `noted` edge is removed, so `_drop_orphans` drops it. `SAME_NOTE = 0.96`, measured 2026-11-11 on `baai/bge-m3`: rewordings 0.71 to 0.97, different instructions on one topic 0.72 to 0.95, unrelated 0.43 to 0.59, so embeddings cannot tell a rewording from a different instruction and only merge near-identical text; re-measure after changing the embedding model. A model that leaves `replaces` out leaves a duplicate or contradicting note, never a lost one. `about` names resolve like fact objects; an empty `about` links the User node; `_drop_orphans` drops note nodes with no `noted` edge. Known limit: notes go to the agent that wrote the final answer. In team mode, and when the orchestrator asks a specialist as a tool and writes the answer itself (research always works this way), the notes are the orchestrator's, so the research agent gets none for now. Against duplicate wording (the same fact saved as `has_name`/`is_named`/`is`): `Fact` maps known wordings to a `STANDARD` relation (`ALIASES`); `EXTRACT_PROMPT` lists `STANDARD` (a test checks it) and the extractor's message lists the user's other relations to reuse; a file -> User link is turned to User -> file; and `_keep_one_edge` keeps one learned edge per node pair (a standard relation beats invented ones, the newest invented one beats older ones, two different standard ones both stay; card edges are left alone). The profile split: `recall_profile` (SQL only, the newest `RECALL_FACTS` edges at the User node whose relation is in `PROFILE`, listed in `PROFILE` order, then by object) returns the bullets and the profile relations present, and fills `AgentContext.profile`/`PROFILE_SECTION`; `recall_facts` (SQL only, newest `RECALL_FACTS` edges at the User node, `PROFILE` relations excluded) fills `AgentContext.memories`/`MEMORIES_SECTION`; both reach the prompt through the chat's snapshot; `search_memory` runs `search_facts`; `_facts_query` leaves out every edge with an `agent` or `note` node at either end, so `recall_profile`, `recall_facts`, `search_facts` and `list_facts` never show notes. `recall_notes` (SQL only, the newest `RECALL_NOTES` 10 per agent by the `noted` edge's `updated_at`) returns `{agent: bullets}`, which fills `AgentContext.agent_notes`; `build_agent(route=...)` renders it as `NOTES_SECTION`. `/api/memories` lists facts and notes (`list_facts`, `list_notes`; a note row carries `agent`) and deletes either (`delete_fact`, cards excluded). `scripts.build_graph` starts the graph once per user (`users.graph_built_at`; new accounts get it at signup, so it never touches them): the old store namespace `("users", user_id, "memories")` (converted, then emptied; otherwise only `forget_user` touches it) and every turn of every past chat (`CHAT_BATCH` turns per `extract_from_turns` call, progress in `conversations.mined_turns`, so a rate-limited run resumes), then cards for ready files without one (from their stored chunks). `scripts.build_graph` yields facts only: past turns do not say which agent answered, so no notes are saved from them. `scripts.reindex` re-embeds note nodes together with entities (`reembed_graph`). The store's semantic index (pgvector HNSW only supports ≤2000 dims, so larger `EMBED_DIM` switches to a flat index) still serves chat history.
- Memory snapshot (`app/core/snapshot.py`): a chat's profile, facts, each agent's notes (`agent_notes`) and other-chat turns (`load_recent_chats`, `CROSS_CHAT_HISTORY`, default on) are frozen in `conversations.memory_snapshot` (jsonb) with `snapshot_at`, and become `AgentContext.user/profile/memories/recent_chats/bootstrap`. `chat_snapshot` reuses the saved snapshot while the chat's last turn (`updated_at`) is within `MEMORY_SNAPSHOT_MINUTES` (default 60) and the saved snapshot has `profile` and `agent_notes` keys (older ones are rebuilt), else calls `build_snapshot` and saves it (`save_snapshot`). Deleting a fact or a note (`/api/memories`), a file (`features/documents/routes.py`) or a conversation calls `clear_snapshots(user_id)`, which clears every chat's snapshot of that user and stamps `snapshot_at`. Race rule: `save_snapshot` drops a build that started before or at that stamp, since it may hold deleted data. Facts learned in a chat are in its history, so they are not added to the snapshot. `bench_chat` calls `build_snapshot(None, ...)` once per scenario, so its runs have no other-chat turns.
- BOOTSTRAP (`bootstrap_due`, `app/core/snapshot.py`): decided once per snapshot, in `build_snapshot`. It is on when the profile has neither `has_role` nor `works_at`, or has no `has_goal`, and either this conversation's `conversations.bootstrap_ran` is true or fewer than `BOOTSTRAP_CHATS` of the user's conversations have it (`BOOTSTRAP_CHATS` = 0 is off). `save_snapshot` sets `bootstrap_ran` in the same update when the snapshot's `bootstrap` is true. `clear_snapshots` leaves `bootstrap_ran` alone, so deleting a fact, file or chat does not restart onboarding; deleting a conversation removes its row and frees one slot. The question is written by the orchestrator (`orchestration.md`), and its answer is saved by the usual `remember_turn` path, like any finished turn.
- Cross-chat history search: after a finished turn a `BackgroundTask` indexes it under `("users", user_id, "history")` (`save_turn`) for the `search_chat_history` tool. Deleting a conversation also deletes its history items (`forget_conversation`).
- Chat memory (`app/core/chat_memory.py`, per chat, not cross-chat, not facts): the table `chat_data` keeps what a chat's specialists fetched, one row per tool call (`turn`, `step`, `agent`, `tool`, `args`, `content`, `artifacts`; `user_id` and `conversation_id` ON DELETE CASCADE). `RemoteAgent.ainvoke` saves after each call with `entries_from` and `save_entries`: memory tools and error results are skipped, research's `findings` become one row, and each result is cut to `chat_data_entry_chars`. `step` is `configurable["chat_step"]` (a team task id, `chart`, `ask`, or `reply`). Reading: `render` makes one note of at most `chat_data_chars` (headers for every entry, full content for the newest while the budget lasts), passed as `AgentContext.chat_data` and rendered last by `CHAT_DATA_SECTION`; `chat_note` (orchestrator) and the team plan and judge read it too. `known_tables` merges the chat's saved tables with this turn's (by id) for the chart tools and the write-up. Chat data is not extracted into facts, not in the memory snapshot, and agent servers only read it (`READER_TABLES`).
