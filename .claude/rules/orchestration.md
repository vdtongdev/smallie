App startup, routing, the orchestrator and the chat stream.

**Startup (`app/api/main.py` lifespan):** creates app tables (`app/core/db.py`, all app tables live there so every `init_db()` caller creates them; SQLAlchemy Core, `metadata.create_all`, no migrations), opens the LangGraph `AsyncPostgresSaver` + `AsyncPostgresStore` on one shared `AsyncConnectionPool` (`app/core/memory.py`), runs each feature's `start` hook, and builds the assistant graph once into `app.state.assistant`. The SQL agent introspects the schemas in `SCHEMAS` (`market`) (columns, FKs, comments, sample rows) at build time and bakes it into its system prompt, so schema changes need a restart.

**Routing (`app/orchestration/`):** `graph.py` builds `START → router → <route> | orchestrator` from `AGENTS`; each agent node is a `RemoteAgent` (see **Remote agents**) that gets the thread's messages and the runtime context with every call, so the main app's thread stays the only copy of a conversation. Agents with `answers_directly` go to END, research goes on to the orchestrator. Exception (`fallback.py`): when the router picked the agent itself (`direct`; not forced, not a handoff) and `AgentSpec.gave_up` (no final text, every tool result matched the spec's `no_result`, or a short reply matching `NOT_FOUND`), the `fallback` node removes the attempt from the thread and puts its summary in `failed`/`attempt` for the orchestrator (hidden `ATTEMPT_MESSAGE`, no `handoff` tool then); its update becomes a `fallback` SSE event, on which the UI drops the streamed reply. The orchestrator's `no_repeats` tool middleware skips an identical tool call within one message and caps `ask_<route>` at `MAX_ASKS` per message (the failed attempt counts). `router.py` never calls a model: forced by `AgentContext.agent` (`/api/chat/<route>`), or `obvious_route` when exactly one available agent's `hints`/`matches` fire (keywords, a known ticker, a file name) and no other agent is mentioned (`mentioned_routes`, which adds `RouteInfo.mentions`: "my resume" next to a ticker is not obvious); everything else → `orchestrator`.

**Orchestrator (`app/orchestration/orchestrator.py`, prompts in `orchestration/prompts.py`, formats in `orchestration/formats/`):** a node wrapping a `build_agent(name="orchestrator")` the way the old writer step did: it took over the old research writer's formats and citation rules; it invokes the agent on the thread (plus a hidden `FINDINGS_MESSAGE` named `research_findings` when the router sent the message to research first) and puts only the final `AIMessage` into the thread, so delegated results and search output never reach later prompts (they still stream as tool events). Tools: `ask_<route>` per spec with a `tool_description` (invokes the compiled specialist with just the self-contained question and `context=runtime.context`, result capped at `RESULT_CHARS`; parallel calls run concurrently), `handoff(agent)` (`return_direct`; the node then returns `Command(goto=<route>)`, the specialist answers on the thread without the orchestrator's tool call in it, and the top-level update's `route` becomes a second `agent` SSE event), and the research MCP `tavily_tavily_search`/`knowledge_wikipedia_search` (`mcp_tools()`; `web_search_rule` tells it to run Wikipedia alongside the web search). `prefer_handoff` (a `wrap_model_call` middleware) turns a first step that asks exactly one directly-answering specialist into a handoff, because free models almost never pick `handoff` themselves, unless `AgentContext.mentioned` (the routes `mentioned_routes` finds for the latest message) names another one, so it can still ask that one next step and combine; it also strips other calls next to a handoff (`return_direct` only ends the loop when every call in the step is). The prompt makes figures about stocks/companies and anything in the user's files come from sql/docs, never the model's memory, so mixed questions ask every needed specialist in one step; `COMPOSE_SECTION` has the rules for combining their results into one answer (and for re-asking docs, naming the file, when it found nothing in a listed file). `compose_section` (via `build_agent(prompt_extra=...)`) adds the per-request `AgentContext.notes` (unavailable specialists, document names, previous answer's agent from `MESSAGE_ROUTES`, `MENTIONS_NOTE` when several are mentioned) on every call, and the formats + `CITATIONS` + reply language only once the turn has tool results or findings (`is_composing`), so the deciding call stays short. `MESSAGE_ROUTES` here extends the registry's with `orchestrator` (and the removed writer's `report_agent`); the conversations API uses it for badges.

**Chat flow (`app/api/routes_chat.py`):** `POST /api/chat/{auto|team|<route>}` (unknown route → 404; `team` = **Team mode**) → creates/looks up the conversation row → `recall_facts()` (the user's newest graph facts) → `assistant.astream(stream_mode=["messages","updates","custom"], subgraphs=True)` with `thread_id = conversation id` → converted by `_to_events(mode, chunk, namespace)` by `_events_from` into SSE events (`conversation`, `agent`, `step`, `fallback`, `token`, `tool_call`, `tool_result`, `error`, `done`, plus the team events `plan`, `plan_updated`, `wave`, `spoke`, `review`, `synthesize`, `needs_human`, `charts`; `step` = a workflow moved to another step listed in its spec's `steps`) consumed by `app/static/app.js`. Top-level (`namespace == ()`) updates only yield `agent` events (any update with a `route`: the router's choice, the orchestrator's handoff or a fallback) and `fallback` events (an update with `failed`); the agent nodes' top-level updates repeat what their subgraph already streamed. `tool_call`/`tool_result` events from a specialist the orchestrator asked or handed to carry `agent: <route>` (`_asked_route` finds the route segment in the namespace; not when it equals the router's own choice, which stays untagged; `ask_<route>` in `delegation.py` appends `<route>:<tool call id>` to the `checkpoint_ns` it runs the specialist under, because parallel asks share one `tools` node, and a remote agent's chunks are prefixed with that namespace); the UI lists them under that agent's badge in the activity popup (`act.asked`). Tokens from a namespace with a `tools` segment (an agent the orchestrator called as a tool) are dropped, as are `handoff` tool events. Message history lives only in the LangGraph checkpointer; the `conversations` table is just the sidebar index (`kind` = mode it was started with; the sidebar lists all kinds). The UI sends `team` when the Team mode switch is on for a new chat or the opened chat is a team chat, else `auto`; it shows an agent badge per turn and another one when a workflow hands over to its next agent (`step` event; skipped when the label would repeat the badge above), keeps the open conversation in `localStorage` (`conversation_auto`) and reopens it on reload; "New chat" is disabled while a reply streams, and a stream that ends without `done` shows a "connection lost" error.

**Stop and resume:** `POST /api/chat/{conversation_id}/stop` (user-scoped) cancels the run's task in `RUNNING` (in-process; one instance, one worker) and returns `{"stopped": bool}`. The astream loop runs in an inner `pump` task whose end sentinel comes from `add_done_callback`, so after a cancel the stream still sends `stopped` (instead of `done`). A second message while `RUNNING` holds the conversation → 409. `remember_turn` returns early when the run did not finish (no fact extraction, no cross-chat save). `_chat_input` (routes_chat) has three branches, in order: a paused team turn → `Command(resume=message)`; a stopped state (`is_stopped` in `orchestration/stopping.py`: `next` set, no interrupts) → `is_resume` (a resume word in at most `RESUME_MAX_WORDS` = 5 words) gives `None` (plain `astream(None)`), else `add_note` and then the same resume; otherwise a new user message. `add_note` adds the visible `HumanMessage` plus a hidden `HumanMessage(name=STEER)` with `STEER_MESSAGE` (`STEER` in `HIDDEN`; `reply_language` skips named messages): on a team turn through `team.steer()` in the team's own checkpoint, else `aupdate_state` on the parent. Stop record: `("users", user_id, "stopped")` keyed by conversation id, `{"model_calls"}`; `_settle_stop` writes it for a cut-off run, the next run seeds a second `UsageCounter` (`budget`, read by the call cap only) from it, and it is cleared when a run finishes. `GET .../messages` appends `stopped: true` with the team transcript (`_team_transcript`); while stopped it also lists the team subgraph's notes (`_team_notes`, best effort). `_serialize` drops named HumanMessages. Limit: all parallel `ask_*` calls of one tools step rerun after a stop.

**UI:** the chat view has a Readme dialog opened from the header. `app/static/` is served by `NoCacheStaticFiles` (`app/api/main.py`, mounted at `/`), which sends `Cache-Control: no-cache` so browsers revalidate `app.js` after a deploy; `/api` is unaffected.
