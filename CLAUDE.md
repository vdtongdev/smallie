# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

FastAPI app hosting LangChain agents (`create_agent`) behind an orchestrator, with a plain HTML/JS UI (`app/static/`, chat view plus a Readme dialog opened from the header, EN/VI toggle in `i18n.js`). The **orchestrator** answers general questions itself (with a quick web search when needed), hands a message off to one specialist, or asks several specialists as tools and writes the answer (it took over the old research writer's formats and citation rules). Specialists, currently four:
- **docs**: RAG over uploaded PDF/DOCX files (pgvector), answers cite `[filename, p. N]`.
- **sql**: natural-language queries via a read-only role against the `market` schema (200 stocks from yfinance).
- **chart**: draws charts (line/bar/area/pie/scatter, Chart.js in the UI) of the `market` data via `chart_sql`, of a query result already in the chat via `chart_table`, or of inline numbers via `chart_data`.
- **research**: researcher (MCP tools: Tavily web search, Wikipedia/arXiv, optional external Postgres; plus `search_documents` and `run_sql`) whose cited findings the orchestrator writes up (summary, list, structured report, comparison or company brief). The researcher loads skills on demand; the orchestrator gets the formats inlined while writing up.

All LLM and embedding calls go through OpenRouter (OpenAI-compatible API, see `app/core/llm.py`). Every agent must reply in the language of the user's latest message (English or Vietnamese); see `LANGUAGE_RULE` in `app/core/prompts.py`.

Layout of `app/`: `core/` (config, llm, db, memory, auth, accounts, conversations, shared prompts; knows nothing about specific agents), `agents/` (one package per agent: `agent.py` with build + `SPEC`, `tools.py`, `prompts.py`; listed in `agents/registry.py`), `features/` (data an agent uses plus its API, ingestion and background jobs: `documents/`, `market/`; listed in `features/registry.py`), `orchestration/` (router + assistant graph), `api/` (shared routes and `main.py`).

`ARCHITECTURE.md` is the overview for people (the team lead, customers). When a change alters a part, flow, table, tool or deployment step it describes, update it in the same branch. Its section 10 tracks the 0.4.0 remote-agents phases (design `docs/superpowers/specs/2026-10-20-remote-agents-design.md`); its section 11 describes team mode (0.5.0) for people, the code-level description is **Team mode** below.

## Commands

Development is on Windows with `uv`. Postgres 18 (pgvector) runs on **port 5433** in the compose `db` container (`smallie-db`), on Docker Engine inside WSL Ubuntu (no Docker Desktop). Run Docker commands through WSL: `wsl -d Ubuntu -u root --cd "/mnt/c/Users/Asus ROG/projects/smallie" -- docker <args>`. The WSL-installed Postgres (`db/setup_wsl.sh`) is legacy and disabled. No local `docker build` is needed before deploying the main app.

**Run `scripts\dev_db.ps1` before DB tests, the app or `bench_chat`.** WSL stops about 25 s after the last `wsl` command ends (measured on WSL 3.0.3), even with Docker running, and takes Postgres with it. Symptoms: DB tests skipped ("Postgres not running"), or a run that freezes in `psycopg.connect` because WSL stopped mid-run (a stack dump shows `wait_conn`). The script starts a hidden `sleep infinity` WSL session that keeps WSL up until the PC shuts down (or `wsl --shutdown`), runs `docker compose up -d db` and waits until `smallie-db` is healthy. It is safe to re-run. A one-off `wsl ... docker ps` only buys 25 s. If a run is already frozen: Ctrl+C, run the script, rerun.

**The agent servers run in the same compose project.** `docker compose up -d` (through WSL, as above) starts `redis` and `docs`/`sql`/`research`/`chart` on `127.0.0.1:2101`–`2104`, all from the one image `smallie-agent` (`Dockerfile.agent`). The main app needs them: `.env` holds `AGENT_URLS` and `SERVICE_TOKEN`, and startup fails without `AGENT_URLS`. After changing code an agent server runs, rebuild: `docker compose up -d --build`. **Turn off Cloudflare WARP and the SoftEther VPN client before Docker pulls or builds, or before using the stack.** They corrupt WSL's HTTPS traffic. Symptoms: `tls: bad record MAC` from Docker, `decryption failed or bad record mac` from curl, while Windows' own downloads stay fine.

- Tests that need Postgres use the `requires_db` marker from `tests/conftest.py` and are skipped when the DB is unreachable. Skipped DB tests are not a pass: run `scripts\dev_db.ps1` and rerun. `pytest-asyncio` runs in `auto` mode.
- No linter/formatter is configured.

## Architecture

**Startup (`app/api/main.py` lifespan):** creates app tables (`app/core/db.py`, all app tables live there so every `init_db()` caller creates them; SQLAlchemy Core, `metadata.create_all`, no migrations), opens the LangGraph `AsyncPostgresSaver` + `AsyncPostgresStore` on one shared `AsyncConnectionPool` (`app/core/memory.py`), runs each feature's `start` hook, and builds the assistant graph once into `app.state.assistant`. The SQL agent introspects the schemas in `SCHEMAS` (`market`) (columns, FKs, comments, sample rows) at build time and bakes it into its system prompt, so schema changes need a restart.

**Agent registry (`app/agents/`):** each agent is described by an `AgentSpec` (`agents/base.py`): `route` (URL segment, router answer, SSE `agent` event, graph node), `description` (its line in the orchestrator prompt), `labels` (UI badge per language, served by `GET /api/agents` after the orchestrator's own `LABELS`), `build` (compiled agent *or* a small workflow graph, no checkpointer/store), `message_names` (the `AIMessage.name`s it writes), `hints` (regex of words that only fit it) and `route_info(user_id)` (per-request routing data: a prompt note, an extra "obvious" matcher and a weaker `mentions` matcher, or `None` when the agent has nothing for this user, e.g. no documents; docs mentions = distinctive words of the user's file names or resume/CV words). Optional: `prepare(stack)`, awaited in the lifespan before the assistant is built (async setup such as loading MCP tools); `silent_steps`, workflow node names whose tokens `_to_events` drops (registry exports them as `SILENT_STEPS`; tool events still stream); `steps`, workflow node name -> UI labels, announced by a `step` SSE event when that step starts (served by `GET /api/agents`); `tool_description` (non-empty: the orchestrator gets an `ask_<route>` tool); `answers_directly` (default True; False = it only gathers material, like research: never handed off to, and its graph node continues to the orchestrator); `result(state)` (the `ask_<route>` tool's text, default `last_answer`); team mode: `review` (what it can check when asked to critique another agent's draft; empty = never asked), `sources` (data sources it reads: `market_db`, `user_files`, `web`, `external_db`; also what `scope_tools` filters by), `joins` (`mentioned` = takes part when the message points to it, `with_others` = also whenever another agent takes part). `AGENTS` in `agents/registry.py` is the only list.

**Routing (`app/orchestration/`):** `graph.py` builds `START → router → <route> | orchestrator` from `AGENTS`; each agent node is a `RemoteAgent` (see **Remote agents**) that gets the thread's messages and the runtime context with every call, so the main app's thread stays the only copy of a conversation. Agents with `answers_directly` go to END, research goes on to the orchestrator. Exception (`fallback.py`): when the router picked the agent itself (`direct`; not forced, not a handoff) and `AgentSpec.gave_up` (no final text, every tool result matched the spec's `no_result`, or a short reply matching `NOT_FOUND`), the `fallback` node removes the attempt from the thread and puts its summary in `failed`/`attempt` for the orchestrator (hidden `ATTEMPT_MESSAGE`, no `handoff` tool then); its update becomes a `fallback` SSE event, on which the UI drops the streamed reply. The orchestrator's `no_repeats` tool middleware skips an identical tool call within one message and caps `ask_<route>` at `MAX_ASKS` per message (the failed attempt counts). `router.py` never calls a model: forced by `AgentContext.agent` (`/api/chat/<route>`), or `obvious_route` when exactly one available agent's `hints`/`matches` fire (keywords, a known ticker, a file name) and no other agent is mentioned (`mentioned_routes`, which adds `RouteInfo.mentions`: "my resume" next to a ticker is not obvious); everything else → `orchestrator`.

**Orchestrator (`app/orchestration/orchestrator.py`, prompts in `orchestration/prompts.py`, formats in `orchestration/formats/`):** a node wrapping a `build_agent(name="orchestrator")` the way the old writer step did: it invokes the agent on the thread (plus a hidden `FINDINGS_MESSAGE` named `research_findings` when the router sent the message to research first) and puts only the final `AIMessage` into the thread, so delegated results and search output never reach later prompts (they still stream as tool events). Tools: `ask_<route>` per spec with a `tool_description` (invokes the compiled specialist with just the self-contained question and `context=runtime.context`, result capped at `RESULT_CHARS`; parallel calls run concurrently), `handoff(agent)` (`return_direct`; the node then returns `Command(goto=<route>)`, the specialist answers on the thread without the orchestrator's tool call in it, and the top-level update's `route` becomes a second `agent` SSE event), and the research MCP `tavily_tavily_search`/`knowledge_wikipedia_search` (`mcp_tools()`; `web_search_rule` tells it to run Wikipedia alongside the web search). `prefer_handoff` (a `wrap_model_call` middleware) turns a first step that asks exactly one directly-answering specialist into a handoff, because free models almost never pick `handoff` themselves, unless `AgentContext.mentioned` (the routes `mentioned_routes` finds for the latest message) names another one, so it can still ask that one next step and combine; it also strips other calls next to a handoff (`return_direct` only ends the loop when every call in the step is). The prompt makes figures about stocks/companies and anything in the user's files come from sql/docs, never the model's memory, so mixed questions ask every needed specialist in one step; `COMPOSE_SECTION` has the rules for combining their results into one answer (and for re-asking docs, naming the file, when it found nothing in a listed file). `compose_section` (via `build_agent(prompt_extra=...)`) adds the per-request `AgentContext.notes` (unavailable specialists, document names, previous answer's agent from `MESSAGE_ROUTES`, `MENTIONS_NOTE` when several are mentioned) on every call, and the formats + `CITATIONS` + reply language only once the turn has tool results or findings (`is_composing`), so the deciding call stays short. `MESSAGE_ROUTES` here extends the registry's with `orchestrator` (and the removed writer's `report_agent`); the conversations API uses it for badges.

**Agent construction (`app/agents/factory.py`, `build_agent`):** every agent gets its own tools plus `search_memory`/`search_chat_history` (no save tool: see Memory), a `@dynamic_prompt` middleware that appends recalled memories (`MEMORIES_SECTION`) and `prompt_extra(request)` if given, `ModelCallLimitMiddleware` (`MAX_MODEL_CALLS` per message, or `build_agent(max_model_calls=...)`), then `scope_tools` and `refuse_hidden_tools` (team mode, see **Team mode**), then any extra `middleware`; `model=` overrides `OPENROUTER_CHAT_MODEL` (the orchestrator uses `OPENROUTER_ORCHESTRATOR_MODEL`, capped by `ORCHESTRATOR_MAX_MODEL_CALLS`). `OPENROUTER_FALLBACK_MODEL` (comma-separated) is passed to OpenRouter as `models` in `get_chat_model` (server-side fallback, no extra request); `OPENROUTER_QUANTIZATIONS` (e.g. `bf16,fp8`) goes in as `provider.quantizations`, because the cheapest paid providers run fp4, which slips more; `OPENROUTER_PROVIDER_SORT` (e.g. `throughput`) goes in as `provider.sort`, because within the quantization filter OpenRouter's default picks the cheapest and often slowest provider; `temperature=0`, because sampling made weaker models slip words of other scripts into Vietnamese answers; `max_retries=1` because retries also count against the free quota. Per-request data travels in `AgentContext(user_id, user, memories, recent_chats, agent, notes)`; tools read it via `ToolRuntime[AgentContext]`.

**Remote agents (`app/agents/remote.py`, `app/agents/server.py`; design in `docs/superpowers/specs/2026-10-20-remote-agents-design.md`):** each specialist runs as its own LangGraph Agent Server. The main app never imports a specialist's graph; it calls it through `RemoteAgent`.
- **The call.** `build_assistant` builds one `RemoteAgent` per spec from `AGENT_URLS` (a missing route fails at startup; tests pass `agents=local_agents()` from `tests/conftest.py`). `RemoteAgent` wraps `RemoteGraph("agent", ...)` with its own client (`make_client`: no LangSmith key sent, only connection-level retries, `AGENT_TIMEOUT_S` plus an `asyncio.timeout` cap).
- **What it sends and keeps.** It sends `asdict(AgentContext)` in the body, `x-service-token` and `x-smallie-user-id`, and drops only `thread_id`, so the run is stateless, with `on_disconnect="cancel"` (a call cut off by the timeout or a closed chat stops on the server instead of spending uncounted calls). On Cloud Run (`K_SERVICE` set) it also sends `Authorization: Bearer` from `id_token(url)` (metadata server, cached until the token's `exp` minus 5 min). Keep `checkpoint_ns`: RemoteGraph uses it to prefix streamed chunks with the parent namespace, and `_to_events` relies on that. Remote JSON becomes messages via `as_message`; `_to_events` skips unknown types. Only `messages`, `findings` and `tools` (the server's tool-call list, see **Team mode**) reach the parent state, so a remote key can't steer routing.
- **Errors and the budget.** Remote `RateLimitError`/`AuthenticationError` are raised again as `openai` errors. Before each call, `RemoteAgent` raises `CallBudgetExceeded` once the request's `UsageCounter.model_calls` reaches `MAX_MESSAGE_MODEL_CALLS`. That is a soft backstop on top of the per-agent caps: parallel asks in one step can overshoot it. A team request (`context.agent == TEAM_MODE`) uses `TEAM_MAX_MESSAGE_MODEL_CALLS` instead.
- **The server side.** `server.py`'s `make_graph` (graph `agent` in `langgraph.json`; langgraph-api calls it on every run, so it builds once under a lock) serves the spec named by `AGENT_ROUTE` behind a `run` node (`RUN_NODE`). It runs `prepare`, opens the app's store for `search_chat_history` (`set_history_store`, no `setup()`), and returns only the new messages plus `usage` (model calls, tokens, cost, including nested calls such as research's researcher). `RemoteAgent` adds that `usage` to the counter, since this process can't see remote calls. `_to_events` skips the `run` node's update, because the inner steps already streamed it.
- **Auth.** `server_auth.py` accepts only `x-service-token == SERVICE_TOKEN`, comparing bytes, and fails closed when unset.
- **Agents never call each other** (`test_specialists_cannot_import_remote_graph`). Agent servers don't install fastapi: `Dockerfile.agent` drops the pins that clash with the base image's constraints (`protobuf`, `fastapi`, `opentelemetry-api`), and a test checks that the server never imports it.
- **Database logins.** A server never uses the app database's owner. `DATABASE_URL` is `agent_reader` (`06_agent_reader.sql`): SELECT on `READER_TABLES` only, which `grant_reader` (`app/core/db.py`) grants at the end of every app start, because on a fresh database the tables appear only then. So server-side code paths must not write: no DDL, no TTL refresh (`refresh_ttl=False`), PGVector with `create_extension=False` (the documents feature's `start` creates its tables). `DATABASE_URI` is `agent_server` (`05_agent_databases.sql`), owner of the `agent_<route>` databases; the app database refuses it (`06` revokes CONNECT from PUBLIC). Stock queries go through `agent_readonly`.
- **Compose settings.** Each server has its own database `agent_<route>` (created by `dev_db.ps1`) and Redis database; on Cloud Run they share one Redis, separated by `REDIS_KEY_PREFIX`. It runs with `BG_JOB_MAX_RETRIES=1`: that value counts attempts, so `0` never runs; `1` means a run cut off by a restart is not repeated. `BG_JOB_TIMEOUT_SECS=360` stops a run whose cancel never arrived. It also runs with `LANGGRAPH_POSTGRES_POOL_MAX_SIZE=5` (the Go core reads it too) and `DB_POOL_SIZE=2`. `Dockerfile.agent`'s base image is pinned by digest; upgrade it on purpose.

**Chat flow (`app/api/routes_chat.py`):** `POST /api/chat/{auto|team|<route>}` (unknown route → 404; `team` = **Team mode**) → creates/looks up the conversation row → `recall_facts()` (the user's newest graph facts) → `assistant.astream(stream_mode=["messages","updates","custom"], subgraphs=True)` with `thread_id = conversation id` → converted by `_to_events(mode, chunk, namespace)` by `_events_from` into SSE events (`conversation`, `agent`, `step`, `fallback`, `token`, `tool_call`, `tool_result`, `error`, `done`, plus the team events `round`, `board`, `spoke`, `synthesize`, `needs_human`; `step` = a workflow moved to another step listed in its spec's `steps`) consumed by `app/static/app.js`. Top-level (`namespace == ()`) updates only yield `agent` events (any update with a `route`: the router's choice, the orchestrator's handoff or a fallback) and `fallback` events (an update with `failed`); the agent nodes' top-level updates repeat what their subgraph already streamed. Tokens from a namespace with a `tools` segment (an agent the orchestrator called as a tool) are dropped, as are `handoff` tool events. Message history lives only in the LangGraph checkpointer; the `conversations` table is just the sidebar index (`kind` = mode it was started with; the sidebar lists all kinds). The UI always uses `auto`, shows an agent badge per turn and another one when a workflow hands over to its next agent (`step` event; skipped when the label would repeat the badge above), keeps the open conversation in `localStorage` (`conversation_auto`) and reopens it on reload; "New chat" is disabled while a reply streams, and a stream that ends without `done` shows a "connection lost" error.

**Memory:**
- Short-term: checkpointer, per conversation.
- Long-term: a knowledge graph per user (`app/core/graph.py`) in plain tables `graph_nodes` (kind `user`/`file`/`entity`; file nodes carry `document_id`, entities an `embedding`) and `graph_edges` (`relation`, provenance `source` = `chat`/`document`/`import`, `document_id`, `conversation_id` without FK), both `user_id`-scoped with ON DELETE CASCADE; laid out as vertex + edge tables so a PostgreSQL 20 `CREATE PROPERTY GRAPH` can sit on top (SQL/PGQ was pulled from PG 19). Only facts touching the User node or a file node are kept. Agents never save facts themselves (free models skipped the optional save call, AP-006): after a finished turn whose answer came from the orchestrator (`_answered_by`; sql/chart/docs lookups are skipped to save calls), the `remember_turn` background task runs `extract_facts`, one call of the orchestrator's model with `with_structured_output(FactUpdate, method="function_calling")` and `EXTRACT_PROMPT` (the user's file names go in the human message); Pydantic is the filter (snake_case relation, ≤ 5 triples), and its tokens go into the usage totals. `save_facts` resolves names: user words → the User node, a file name → its file node, else an entity by exact `normalize`d name, then nearest embedding ≥ `SAME_ENTITY` (measured; re-measure after changing the embedding model), else a new node; a relation in `FUNCTIONAL` replaces the user's old edge; orphan entities are dropped. Against duplicate wording (the same fact saved as `has_name`/`is_named`/`is`): `Fact` maps known wordings to a `STANDARD` relation (`ALIASES`); `EXTRACT_PROMPT` lists `STANDARD` (a test checks it) and the extractor's message lists the user's other relations to reuse; a file -> User link is turned to User -> file; and `_keep_one_edge` keeps one learned edge per node pair (a standard relation beats invented ones, the newest invented one beats older ones, two different standard ones both stay; card edges are left alone). `recall_facts` (SQL only, newest `RECALL_FACTS` edges at the User node) fills `AgentContext.memories`/`MEMORIES_SECTION`; `search_memory` runs `search_facts`; `/api/memories` lists and deletes edges (`list_facts`, `delete_fact`, cards excluded). `scripts.build_graph` starts the graph once per user (`users.graph_built_at`; new accounts get it at signup, so it never touches them): the old store namespace `("users", user_id, "memories")` (converted, then emptied; otherwise only `forget_user` touches it) and every turn of every past chat (`CHAT_BATCH` turns per `extract_from_turns` call, progress in `conversations.mined_turns`, so a rate-limited run resumes), then cards for ready files without one (from their stored chunks). The store's semantic index (pgvector HNSW only supports ≤2000 dims, so larger `EMBED_DIM` switches to a flat index) still serves chat history.
- Cross-chat (`CROSS_CHAT_HISTORY`, default on): `routes_chat` loads the last turns of the user's 3 most recent other chats from their checkpoints (`load_recent_chats`, passed as `AgentContext.recent_chats`, appended as `RECENT_CHATS_SECTION`), and after a finished turn a `BackgroundTask` indexes it under `("users", user_id, "history")` (`save_turn`) for the `search_chat_history` tool. Deleting a conversation also deletes its history items (`forget_conversation`).

**Research workflow (`app/agents/research/agent.py`):** `StateGraph(ResearchState)` with one node `gather`, compiled as `research`. `gather` invokes the researcher (`research_agent`, cap `RESEARCH_MAX_MODEL_CALLS`) inside the node with `context=runtime.context` (it still streams as a nested subgraph) and stores its final notes in `findings` (or its last raw tool results via `findings_from` when it hit the cap), never in the messages: as a route node the assistant's `findings` key carries them to the orchestrator (which clears it), as the `ask_research` tool `findings_result` returns them. `gather` is a silent step. When Tavily loaded, the researcher prompt gets `WEB_ALONGSIDE_WIKI` (every Wikipedia search comes with a web search in the same step, except for arXiv questions). The orchestrator's citation format (`CITATIONS` in `COMPOSE_SECTION`: `[n]` numbers in paragraphs plus a numbered Sources list at the end, `([source](URL))` at the end of bullets) gets deep links from the researcher: its notes cite `[source: <id> | "quote"]`, where the id (`S` + 4 hex of the URL's sha1, `source_id`) comes from the `[source ids]` list that the `cite_by_id` tool middleware appends to every tool result (`source_index` finds the URLs: Tavily JSON entries and every URL in text results with the text before it as title; `page_text` strips the list again for `pages_from`). Ids keep the notes short, since writing them is the researcher's slowest step (the prompt also caps their length). `expand_source_ids` turns them back into `[source: Title | URL | "quote"]` (unknown ids are dropped, the quote still finds the page), which `link_sources` (in `gather`) rewrites as `[source: <label> | <URL> | passage: <URL>]`, checked against the pages in the researcher's tool results (`pages_from`: Tavily JSON entries and `wikipedia_page` text) plus the whole article of each cited Wikipedia page (`with_wikipedia_articles` → `knowledge.wikipedia_article`, a plain HTTP fetch, not a model call). The first URL is the Wikipedia section the quote is in (or the page), so paragraph facts from one section share one reference number; the passage link adds `:~:text=` and is what list items cite; the label is the page's own title (plus section name). A quote not on any page gets no passage link; a source written without a URL gets the URL of the page containing its quote, or of the one page whose domain matches its label; the write-up rules also name the reply language (`reply_language` in `core/prompts.py`), and `knowledge_wikipedia_page` shows each heading's section URL and, with `section=`, that section plus the articles it links to (so list items can cite their own page). The format is tied to `linkCitations` in `app.js`, which turns `[n]` into superscripts that scroll to item n of the message's last top-level `<ol>`. Don't name an inner node like a route (`research`), or the namespace filter would silence the whole workflow.

**MCP (`app/core/mcp.py`, `open_mcp_tools`):** remote servers (`streamable_http`/`sse`) via `MultiServerMCPClient(tool_name_prefix=True).get_tools(server_name=...)`, so each tool call opens its own session. Local FastMCP servers run in-process via `mcp.shared.memory.create_connected_server_and_client_session`, whose session lives on the lifespan exit stack; **don't use stdio servers**, because asyncio subprocesses fail on Windows' `SelectorEventLoop`, and the Cloud Run image has no Node. Tool names are `<server>_<tool>` (Tavily's become `tavily_tavily_search`/`tavily_tavily_extract`; its credit-hungry `crawl`/`map`/`research` tools are dropped via `SKIPPED_TOOLS` in the research agent). A failing server is logged and skipped. The research servers are configured in `app/features/research/sources.py` (Tavily via `Authorization: Bearer` header when `TAVILY_API_KEY` is set, extra JSON from `MCP_SERVERS`) and live in `app/features/research/mcp_servers/` (`knowledge`: Wikipedia/arXiv over `httpx`, `transport` is swappable for tests; `external_db`: `EXTERNAL_DATABASE_URL` through `readonly_engine()` + `execute_readonly(..., engine)`, the same guard as the SQL agent).

**Skills (`app/agents/skills.py`):** `<dir>/<name>/SKILL.md` with `name`/`description` frontmatter; `skills_section()` goes into the system prompt, `make_load_skill_tool()` returns the body on demand. `skills_inline()` puts every body into the prompt instead; the orchestrator uses it for the answer formats because small models skip the optional `load_skill` call and then ignore the format. Researcher skills are in `app/agents/research/skills/researcher/`, answer formats in `app/orchestration/formats/`. Any agent can reuse this.

**Documents:** upload (`app/features/documents/routes.py`) saves to `uploads/<user_id>/<doc_id>.<ext>` and runs `process_document` (`card.py`) as a FastAPI background task: `ingest_document` (status `processing` → `ready`/`failed`; returns the chunks), then `write_card`, one best-effort model call on the first `CARD_CHARS` (`DocumentCard`: type, summary, ≤ 10 entities, `CARD_PROMPT`) that sets `documents.summary` and writes File -mentions-> Entity edges (`save_card`); a failed card never changes the status. Chunks go into the `langchain_postgres` PGVector collection `documents` with deterministic ids `"{document_id}:{i}"` (used for deletion) and `user_id`/`document_id` in metadata. The docs `route_info` note shows the newest `MAX_CARDS` files with their summary. `search_documents(query, entity="")` runs `search_with_graph`: `documents_for` scopes the passage search to the files linked to `entity` (or a file named so), else to known entity names found in the query (weak models skip optional arguments, AP-006), else, and when the scoped search finds nothing, it searches every file. Deleting a document cascades to its file node and card edges; `remove` then calls `drop_orphans`.

**Accounts and user isolation:** `app/core/auth.py::get_current_user` is the *only* place identity is decided: the signed session cookie holds the `user_id` of the logged-in account (401 if missing or the account was deleted). People create accounts (name, username, password) via `POST /api/signup`, capped at `MAX_ACCOUNTS` (default 20, admin not counted, enforced under a Postgres advisory lock). Account rows live on the `users` table and are handled in `app/core/accounts.py` (scrypt hashes; passwords never leave `accounts.py`/`auth.py`). The `admin` account keeps the old shared user id `"team"` (so it owns the pre-accounts data), logs in with `APP_PASSWORD` (no stored hash; `SESSION_SECRET` is then required) and can list, reset and delete accounts (`app/api/routes_admin.py`; deletion removes checkpoints and store items, then calls each feature's `delete_user_data`, e.g. chunks and `uploads/<user_id>/`; documents, conversations and the graph go with the `users` row via ON DELETE CASCADE). `scripts.claim_anonymous_data` moves data of old `anon-*` users to the admin. The account's name and username reach the agents as `AgentContext.user` (`USER_SECTION`). Everything else — DB rows, vector search filter `{"user_id": {"$eq": ...}}`, memory namespace, upload dir — is keyed by `user_id`. Preserve this scoping in any new query or tool.

**Charts and tables (`app/agents/chart/`, `app/agents/artifacts.py`):** data travels as ToolMessage *artifacts*, which the model never sees: `run_sql` (and `chart_sql`) return the pipe table capped at `SQL_MAX_ROWS` as content (footer names the table id) and the whole result (≤ `TABLE_MAX_ROWS`, JSON-safe, from `query_readonly`/`make_table` in `sql/tools.py`) as `{"tables": [...]}`; the chart tools return a short `summary()` as content and the `ChartSpec` (`chart/spec.py`: ≤ 8 series in fixed palette order, pies folded to 8 slices with "Other", scatter ≤ 3 series, > 500 points downsampled) as `{"charts": [...]}`. So no model ever copies data points. `rows_to_spec` pivots long rows by `series_column`. `chart_table` finds tables by id in `runtime.state["messages"]` (`artifacts_from` also reads `AIMessage.additional_kwargs`); the chart agent's `prompt_extra` lists the thread's tables (`table_note`, marking the ones already charted via `ChartSpec.table_id`), and its prompt says to reuse a listed table for "plot that" and for repeated or reworded requests of the same data; as a safety net `chart_sql` reuses an earlier table whose query is the same (`same_query`: case, spacing and `;` ignored) instead of running it again. `make_ask_tool` (`app/agents/delegation.py`, shared by the orchestrator) returns the specialist's tables/charts as its artifact, and the orchestrator (which also has `chart_table`/`chart_data`, and sees `TABLES_SECTION` while writing up) copies its turn's artifacts into its final answer's `additional_kwargs` — `langchain_openai` drops unknown `additional_kwargs` keys, so they never reach a prompt. `_to_events` adds `charts` to `tool_result` events (tables stay on the server); `_serialize` exposes `charts` of tool results and of orchestrator answers. The UI (`app/static/charts.js`) renders a card per chart id (dedupe by `data-chart-id`), with the dataviz reference palette as `--series-1..8` in `style.css` (separate light/dark steps; charts rebuild on a scheme change), crosshair tooltips on lines, a data table and PNG download. The chart agent is obvious through its `HINTS` only and `overrides=("sql",)` ("chart AAPL" matches both; a ticker alone stays sql); `SQL_RULES` in `sql/prompts.py` is shared by the sql and chart prompts.

**SQL safety:** the SQL agent connects with `READONLY_DATABASE_URL` as `agent_readonly` (created in `db/init/03_readonly_role.sql`, extended in `04_market_schema.sql`: SELECT-only on `market`, read-only transactions, 10s timeout, no access to app tables). `execute_readonly` additionally rejects anything that isn't a single `SELECT`/`WITH` and caps rows at `SQL_MAX_ROWS`. The prompt shows schema-qualified table names. To target another database, change `READONLY_DATABASE_URL` and `SCHEMAS` in `app/agents/sql/tools.py` (`get_readonly_engine` is in `app/core/db.py`).

**Stock data (`app/features/market/`):** `scripts.load_stocks` → `load_market()` re-applies the idempotent `db/init/04_market_schema.sql` (so existing DBs get the schema and grants), inserts placeholder `stocks` rows, refreshes profiles from `yf.Ticker(t).info` (one request per ticker, retried), then `yf.download` in batches of 50 and upserts `daily_prices` via COPY into a temp table (setting `updated_at`; `/api/market/status` reports the newest price/profile `updated_at` as "last updated" in the Readme). Incremental by default: starts `OVERLAP_DAYS` before `max(trade_date)`. It writes as the owner (`DATABASE_URL`) and can run while the app is up. yfinance's `dividendYield` is already a percentage.

**Daily update (`app/features/market/scheduler.py`):** the market feature's `start` hook starts `run_daily()` as an asyncio task when `MARKET_UPDATE_TIME` is set (cancelled on shutdown via the exit stack). It catches up once at startup if `max(trade_date)` is older than `latest_session()`, then sleeps until `next_run()` (weekdays, `America/New_York`; needs `tzdata` on Windows). `run_update()` runs `load_market` in a thread under `update_lock()` (a Postgres advisory lock also taken by `scripts.load_stocks`, so multiple workers or a manual run never overlap). Profiles are refreshed only when older than 7 days. Failures are logged and retried 3 times, 15 min apart; the task never dies. There's no holiday calendar: on a holiday the run just upserts nothing.

## Team mode

Design: `docs/superpowers/specs/2026-10-23-agent-team-design.md`, section "Phase C v2: round table". Phase A (shared rooms) is planned, not built. The UI switch turns it on for a new chat (`POST /api/chat/team`; an opened chat keeps its `kind`, served by `GET /api/conversations`). With `context.agent == TEAM_MODE` the router answers `team` without rules.

**Round table (`app/orchestration/team.py`, `build_team`; prompts `ROUND_MESSAGE`, `CONFLICT_MESSAGE`, `BOARD_PROMPT`, `TEAM_MESSAGE` in `orchestration/prompts.py`):** the `team` node of the assistant graph is a subgraph `pick -> speak x N -> judge -> synthesize`, with `pause` on a question.
- `pick`: `participants()` = the agents the latest message points to (`is_mentioned`; of an `overrides` pair only the winner) plus every `joins == "with_others"` agent when another one takes part. Nobody mentioned: the orchestrator answers as in normal mode (a handoff is run on the thread), no rounds. Otherwise it resets `team`/`speeches` (`RESET`) and starts round 1 with one `Send("speak")` per participant.
- `speak`: invokes the agent (remote or local) with `ROUND_MESSAGE` as a last hidden `HumanMessage(name=TEAM)` and `AgentContext.sources = spec.sources`, so it uses only its own sources. A failed agent becomes an entry with `failed: True`; `RateLimitError`/`AuthenticationError` propagate.
- `judge`: `ask_board` makes one structured call (`Board`: agreements, differences, conflicts, question) from the user message and each agent's newest answer; `clean` makes the board safe to route on. A board failure becomes an empty board with `forced`. A conflict with a non-empty `fixable_by` and no question starts a conflict round for those agents only (`CONFLICT_MESSAGE`: the conflict, the other side's answers, the agent's own earlier answer), up to `TEAM_MAX_ROUNDS` conflict rounds after round 1. Past the cap, or after a failure, `forced` is set and the write-up states the conflict instead of settling it.
- `synthesize`: one participant that answers directly, no conflicts, not `forced`: that agent's answer stands (no `synthesize` event, no extra call). Otherwise the orchestrator writes the answer from `TEAM_MESSAGE` (answers, explained differences, open conflicts), passed as `team_note` (hidden message named `TEAM_MODE`, in `HIDDEN`, so `is_composing` is true and it writes without tools); if it hands off instead, the joined answers stand. Only the final `AIMessage` joins the thread; the transcript (`participants`, `rounds`, `boards`, `forced`) goes on its `additional_kwargs["team"]` with the turn's tables/charts, so a reload shows them. The orchestrator also records the routes it asked in `additional_kwargs["asked"]`.

**Board rules:** the board never decides by the kind of source (database, file, web, model): any source can be wrong, and the judge uses no outside knowledge. A difference counts as explained only when every side has a source and an as-of date and the explanation fits the size of the gap (a date gap explains a small move, not a multiple). `clean` enforces the first part in code: a difference with no sides, or a side without source or date, becomes a conflict (`issue` "a side has no source or date"). `routes` keep only agents that answered, `fixable_by` only the conflict's own routes. When several independent dated sources agree against one, the `issue` says so and the write-up says which value stands alone. `question` is set only for information only the user has.

**Pause and resume:** a non-empty `question` makes `judge` emit `needs_human` and go to `pause`, which calls `interrupt` and nothing else (the node reruns from its start on resume); the question joins the thread as an orchestrator `AIMessage`. `_chat_input` (routes_chat) turns the next `team` message into `Command(resume=message)` while `aget_state(config).interrupts` is set; the reply joins the thread and goes back to `judge`. `remember_turn` returns early when the snapshot has interrupts. `GET .../messages` appends the pending question with `pending: true`.

**Independent sources:** `scope_tools` (`wrap_model_call`, `agents/factory.py`) offers a team request only the tools whose `TOOL_SOURCE` tag (`tool.metadata`) is in `context.sources`; untagged tools (memory, skills) stay. A model may still call a hidden tool, because prompts name it, so `refuse_hidden_tools` (`wrap_tool_call`) answers it with an error ToolMessage; both use `_in_scope`. Tags: `run_sql` and `chart_sql` `market_db`, `search_documents` `user_files`, research's MCP tools via `tag_mcp` (`tavily_*`/`knowledge_*` `web`, `external_db_*` `external_db`). `research_prompt_extra` builds the researcher's source list, skills and market schema per request from `context.sources`, so a team researcher is not told about sources it cannot use.

**Transcript and tools:** `ToolRecorder` (`agents/base.py`, async callback) records each tool call as `{name, args, result}` (result cut to `TOOL_RESULT_PREVIEW`), inner calls of a workflow included, memory tools excluded. In-process, `speak` passes it in the config; an agent server runs its own and returns the list as `tools` in its result (`server.py`), which `RemoteAgent` passes on. Without either, `_tools(turn)` scans the messages.

**Custom events (stream mode `custom`, `get_stream_writer`):** `speaker` is internal: `{agent, ns}` tells `_events_from` which `speak:<task id>` namespace runs which agent, and is dropped. `TEAM_EVENTS` reach the UI: `round` (`round`, `max_rounds` = `TEAM_MAX_ROUNDS` + 1, `kind` answer/conflict, `agents`), `board` (the round's `Board` plus `forced`), `spoke` (an agent's final `text` and `tools`), `synthesize` (only on a write-up), `needs_human` (`question`). `_events_from` finds the namespace segment that is in `speakers`: `token`/`tool_call`/`tool_result` events inside it get that `agent`, and `_to_events(in_round=True)` lets silent steps stream (research's notes are its answer).

**UI (`app/static/app.js`):** every reply, team or not, has a status line (spinner, round title, agent badges, "using <tool>", "writing"; afterwards the round count and the explained differences) and an **Activity** button opening a popup (`renderActivity`) with the rounds, each agent's answer and tool calls, the board and a pending question. There are no inline tool lines in the chat. A reload builds the popup from `message.team` (`teamActivity`) or the tool messages.

**Language:** `REPLY_LANGUAGE` is appended on every orchestrator call (from `reply_language()` of the user's messages, hidden ones left out); `ROUND_MESSAGE`, `CONFLICT_MESSAGE`, `BOARD_PROMPT` and `TEAM_MESSAGE` take `{language}`. `MEMORIES_SECTION` ends with a line that a stored language preference never changes the reply language (AP-007).

**Settings:** `TEAM_MAX_ROUNDS` (4), `TEAM_MAX_MESSAGE_MODEL_CALLS` (30, `RemoteAgent`'s guard for team requests), `OPENROUTER_JUDGE_MODEL` (the board's model; empty = `OPENROUTER_ORCHESTRATOR_MODEL`, then `OPENROUTER_CHAT_MODEL`). A set judge uses `get_chat_model(..., exact_model=True)`: no quantization filter (closed models list none, so the filter leaves them no provider) and no `OPENROUTER_FALLBACK_MODEL`. Measured: with Gemma as judge a planted wrong figure was not flagged (29 calls, 189 s); `deepseek/deepseek-v4.1-flash` flagged it in 1 round / 9 calls / 99 s and settled the plain scenarios in 1 round / 6 calls (49 s; chart 74 s), under $0.01 per message; Haiku 5.5 was faster per call but looped 4 rounds on a small date gap.

## Adding an agent or workflow

1. Create `app/agents/<name>/` with `tools.py` (tools read per-user data via `ToolRuntime[AgentContext]`; keep the `user_id` scoping), `prompts.py` (system prompt ending with `LANGUAGE_RULE` and `MEMORY_RULE`, a one-line `ROUTE_DESCRIPTION` and, if the orchestrator may call it as a tool, a `TOOL_DESCRIPTION`) and `agent.py` (`build_agent(name="<name>_agent", ...)` and a `SPEC` that also sets `review`, `sources` and `joins` for team mode). Tag each data tool with its source: `metadata={TOOL_SOURCE: "<source>"}` (untagged tools are never hidden).
2. Append the `SPEC` to `AGENTS` in `app/agents/registry.py`.
3. Add routing tests in `tests/test_router.py` (its hints route to it) and, if it has a `tool_description`, check `agent_lines` in `tests/test_orchestrator.py`.

4. Give it an agent server: one service block in `docker-compose.yml` (copy another, next port and Redis database), its database in `db/init/05_agent_databases.sql`, and its URL in `AGENT_URLS` (`.env`, the `.env.example` comment, and the deploy config). `tests/test_compose.py` checks all three.

No router, orchestrator, API, UI or `main.py` changes are needed. If the agent needs its own data (tables, ingestion, routes, background jobs, per-user cleanup), add a feature in `app/features/<name>/` with a `Feature` (`features/base.py`) appended to `features/registry.py`, and put its tables in `app/core/db.py`.

A multi-step workflow is one entry (research is a one-step example that leaves the writing to the orchestrator via `answers_directly=False`): `build` returns a `StateGraph` with `messages` in its state (plus its own keys, e.g. findings), each step a `build_agent(...)`, compiled with `name=`; list every inner agent name in `message_names`. `_to_events` streams tokens of every inner `model` node, so filter by `namespace` if only the last step should stream.
