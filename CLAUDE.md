# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

FastAPI app hosting LangChain agents (`create_agent`) behind a router, currently three, with a plain HTML/JS UI (`app/static/`, chat view plus a Readme dialog opened from the header, EN/VI toggle in `i18n.js`):
- **docs**: RAG over uploaded PDF/DOCX files (pgvector), answers cite `[filename, p. N]`.
- **sql**: natural-language queries via a read-only role against the `market` schema (200 stocks from yfinance).
- **research**: a workflow, researcher (MCP tools: Tavily web search, Wikipedia/arXiv, optional external Postgres; plus `search_documents` and `run_sql`) → report writer (summary, list, structured report, comparison or company brief). The researcher loads skills on demand; the writer gets its formats inlined.

All LLM and embedding calls go through OpenRouter (OpenAI-compatible API, see `app/core/llm.py`). Every agent must reply in the language of the user's latest message (English or Vietnamese); see `LANGUAGE_RULE` in `app/core/prompts.py`.

Layout of `app/`: `core/` (config, llm, db, memory, auth, accounts, conversations, shared prompts; knows nothing about specific agents), `agents/` (one package per agent: `agent.py` with build + `SPEC`, `tools.py`, `prompts.py`; listed in `agents/registry.py`), `features/` (data an agent uses plus its API, ingestion and background jobs: `documents/`, `market/`; listed in `features/registry.py`), `orchestration/` (router + assistant graph), `api/` (shared routes and `main.py`).

## Commands

Development is on Windows with `uv`. Postgres (pgvector) runs on **port 5433** directly in WSL (`db/setup_wsl.sh`; start it with `wsl -d Ubuntu -u root service postgresql start`; it stops when WSL idles, so start it again before running DB tests). Local development doesn't use Docker; `docker compose up -d` is only an alternative setup, and no local `docker build` is needed before deploying.

```powershell
uv sync                                            # install deps into .venv
uv run uvicorn app.api.main:app --reload --loop asyncio:SelectorEventLoop
uv run pytest                                      # all tests
uv run pytest tests/test_sql.py::test_name         # single test
uv run python -m scripts.reindex                   # after changing OPENROUTER_EMBED_MODEL or EMBED_DIM (app stopped)
uv run python -m scripts.load_stocks               # first load / manual refresh (--full, --prices-only); the app updates daily itself
gcloud run deploy smallie --source . --region asia-southeast1 --allow-unauthenticated --env-vars-file cloudrun.env.yaml --memory 1Gi --cpu 1 --no-cpu-throttling --min-instances 0 --max-instances 1 --timeout 900   # deploy
```

- `--loop asyncio:SelectorEventLoop` is required on Windows: psycopg's async driver (checkpointer/store) fails on the default Proactor loop. Any standalone async script must do the same (see `scripts/reindex.py`).
- Tests that need Postgres use the `requires_db` marker from `tests/conftest.py` and are skipped when the DB is unreachable. `pytest-asyncio` runs in `auto` mode.
- No linter/formatter is configured.

## Architecture

**Startup (`app/api/main.py` lifespan):** creates app tables (`app/core/db.py`, all app tables live there so every `init_db()` caller creates them; SQLAlchemy Core, `metadata.create_all`, no migrations), opens the LangGraph `AsyncPostgresSaver` + `AsyncPostgresStore` on one shared `AsyncConnectionPool` (`app/core/memory.py`), runs each feature's `start` hook, and builds the assistant graph once into `app.state.assistant`. The SQL agent introspects the schemas in `SCHEMAS` (`market`) (columns, FKs, comments, sample rows) at build time and bakes it into its system prompt, so schema changes need a restart.

**Agent registry (`app/agents/`):** each agent is described by an `AgentSpec` (`agents/base.py`): `route` (URL segment, router answer, SSE `agent` event, graph node), `description` (its line in the router prompt), `labels` (UI badge per language, served by `GET /api/agents`), `build` (compiled agent *or* a small workflow graph, no checkpointer/store), `message_names` (the `AIMessage.name`s it writes), `hints` (regex of words that only fit it) and `route_info(user_id)` (per-request routing data: a prompt note and an extra "obvious" matcher, or `None` when the agent has nothing for this user, e.g. no documents). Optional: `prepare(stack)`, awaited in the lifespan before the assistant is built (async setup such as loading MCP tools), and `silent_steps`, workflow node names whose tokens `_to_events` drops (registry exports them as `SILENT_STEPS`; tool events still stream), and `steps`, workflow node name -> UI labels, announced by a `step` SSE event when that step starts (served by `GET /api/agents`). `AGENTS` in `agents/registry.py` is the only list; its first entry is the router's default.

**Routing (`app/orchestration/`):** `graph.py` builds `START → router → <route> → END` from `AGENTS`; agents are subgraph nodes, so they share the parent's thread, checkpointer, store and runtime context. `router.py` returns `{"route": ...}`: forced by `AgentContext.agent` (`/api/chat/<route>`), the only available agent (no documents → `sql`), `obvious_route` when exactly one available agent's `hints`/`matches` fire (keywords, a known ticker, a file name), all without a model call; otherwise one non-streaming call with `ROUTER_SYSTEM` built from the available agents' descriptions and notes plus a short transcript, parsed by `parse_route`. The previous route comes from `AIMessage.name` via `MESSAGE_ROUTES`.

**Agent construction (`app/agents/factory.py`, `build_agent`):** every agent gets its own tools plus `save_memory`/`search_memory`/`search_chat_history`, a `@dynamic_prompt` middleware that appends recalled memories (`MEMORIES_SECTION`), and `ModelCallLimitMiddleware` (`MAX_MODEL_CALLS` per message, or `build_agent(max_model_calls=...)`). `OPENROUTER_FALLBACK_MODEL` (comma-separated) is passed to OpenRouter as `models` in `get_chat_model` (server-side fallback, no extra request); `OPENROUTER_QUANTIZATIONS` (e.g. `bf16,fp8`) goes in as `provider.quantizations`, because the cheapest paid providers run fp4, which slips more; `temperature=0`, because sampling made weaker models slip words of other scripts into Vietnamese answers; `max_retries=1` because retries also count against the free quota. Per-request data travels in `AgentContext(user_id, memories, recent_chats)`; tools read it via `ToolRuntime[AgentContext]`.

**Chat flow (`app/api/routes_chat.py`):** `POST /api/chat/{auto|<route>}` (unknown route → 404) → creates/looks up the conversation row → `recall()` top memories for the message → `assistant.astream(stream_mode=["messages","updates"], subgraphs=True)` with `thread_id = conversation id` → converted by `_to_events(mode, chunk, namespace)` by `_events_from` into SSE events (`conversation`, `agent`, `step`, `token`, `tool_call`, `tool_result`, `error`, `done`; `step` = a workflow moved to another step listed in its spec's `steps`) consumed by `app/static/app.js`. Top-level (`namespace == ()`) updates only yield the router's `agent` event; the agent nodes' top-level updates repeat what their subgraph already streamed. Message history lives only in the LangGraph checkpointer; the `conversations` table is just the sidebar index (`kind` = mode it was started with; the sidebar lists all kinds). The UI always uses `auto`, shows an agent badge per turn and another one when a workflow hands over to its next agent (`step` event; skipped when the label would repeat the badge above), keeps the open conversation in `localStorage` (`conversation_auto`) and reopens it on reload; "New chat" is disabled while a reply streams, and a stream that ends without `done` shows a "connection lost" error.

**Memory:**
- Short-term: checkpointer, per conversation.
- Long-term: store namespace `("users", user_id, "memories")` with a semantic index (`fields=["text"]`). pgvector HNSW only supports ≤2000 dims, so larger `EMBED_DIM` switches to a flat index.
- Cross-chat (`CROSS_CHAT_HISTORY`, default on): `routes_chat` loads the last turns of the user's 3 most recent other chats from their checkpoints (`load_recent_chats`, passed as `AgentContext.recent_chats`, appended as `RECENT_CHATS_SECTION`), and after a finished turn a `BackgroundTask` indexes it under `("users", user_id, "history")` (`save_turn`) for the `search_chat_history` tool. Deleting a conversation also deletes its history items (`forget_conversation`).

**Research workflow (`app/agents/research/agent.py`):** `StateGraph(ResearchState)` with nodes `gather` → `write`, compiled as `research`. `gather` invokes the researcher (`research_agent`, cap `RESEARCH_MAX_MODEL_CALLS`) on the thread's messages and stores its final notes in `findings` (or its last raw tool results via `findings_from` when it hit the cap); `write` invokes the writer (`report_agent`) with the messages plus a hidden `FINDINGS_MESSAGE` and returns only its final `AIMessage`, so the shared thread never gets the researcher's tool output. Both are called inside node functions with `context=runtime.context` (they still stream as nested subgraphs). `gather` is a silent step. The writer's citation format (`CITATIONS` in `REPORTER_SYSTEM`: `[n]` numbers in paragraphs plus a numbered Sources list at the end, `([source](URL))` at the end of bullets) gets deep links from the researcher: its notes cite `[source: Title | URL | "quote"]`, which `link_sources` (in `gather`) rewrites as `[source: <label> | <URL> | passage: <URL>]`, checked against the pages in the researcher's tool results (`pages_from`: Tavily JSON entries and `wikipedia_page` text) plus the whole article of each cited Wikipedia page (`with_wikipedia_articles` → `knowledge.wikipedia_article`, a plain HTTP fetch, not a model call). The first URL is the Wikipedia section the quote is in (or the page), so paragraph facts from one section share one reference number; the passage link adds `:~:text=` and is what list items cite; the label is the page's own title (plus section name). A quote not on any page gets no passage link; a source written without a URL gets the URL of the page containing its quote, or of the one page whose domain matches its label; the hand-off message also names the reply language (`reply_language`), and `knowledge_wikipedia_page` shows each heading's section URL and, with `section=`, that section plus the articles it links to (so list items can cite their own page). The format is tied to `linkCitations` in `app.js`, which turns `[n]` into superscripts that scroll to item n of the message's last top-level `<ol>`. Don't name an inner node like a route (`research`), or the namespace filter would silence the whole workflow.

**MCP (`app/core/mcp.py`, `open_mcp_tools`):** remote servers (`streamable_http`/`sse`) via `MultiServerMCPClient(tool_name_prefix=True).get_tools(server_name=...)`, so each tool call opens its own session. Local FastMCP servers run in-process via `mcp.shared.memory.create_connected_server_and_client_session`, whose session lives on the lifespan exit stack; **don't use stdio servers**, because asyncio subprocesses fail on Windows' `SelectorEventLoop`, and the Cloud Run image has no Node. Tool names are `<server>_<tool>` (Tavily's become `tavily_tavily_search`/`tavily_tavily_extract`; its credit-hungry `crawl`/`map`/`research` tools are dropped via `SKIPPED_TOOLS` in the research agent). A failing server is logged and skipped. The research servers are configured in `app/features/research/sources.py` (Tavily via `Authorization: Bearer` header when `TAVILY_API_KEY` is set, extra JSON from `MCP_SERVERS`) and live in `app/features/research/mcp_servers/` (`knowledge`: Wikipedia/arXiv over `httpx`, `transport` is swappable for tests; `external_db`: `EXTERNAL_DATABASE_URL` through `readonly_engine()` + `execute_readonly(..., engine)`, the same guard as the SQL agent).

**Skills (`app/agents/skills.py`):** `<dir>/<name>/SKILL.md` with `name`/`description` frontmatter; `skills_section()` goes into the system prompt, `make_load_skill_tool()` returns the body on demand. `skills_inline()` puts every body into the prompt instead; the research writer uses it because small models skip the optional `load_skill` call and then ignore the format. Research skills are in `app/agents/research/skills/{researcher,reporter}/`. Any agent can reuse this.

**Documents:** upload (`app/features/documents/routes.py`) saves to `uploads/<user_id>/<doc_id>.<ext>` and runs `ingest_document` as a FastAPI background task (status `processing` → `ready`/`failed`). Chunks go into the `langchain_postgres` PGVector collection `documents` with deterministic ids `"{document_id}:{i}"` (used for deletion) and `user_id` in metadata.

**Accounts and user isolation:** `app/core/auth.py::get_current_user` is the *only* place identity is decided: the signed session cookie holds the `user_id` of the logged-in account (401 if missing or the account was deleted). People create accounts (name, username, password) via `POST /api/signup`, capped at `MAX_ACCOUNTS` (default 20, admin not counted, enforced under a Postgres advisory lock). Account rows live on the `users` table and are handled in `app/core/accounts.py` (scrypt hashes; passwords never leave `accounts.py`/`auth.py`). The `admin` account keeps the old shared user id `"team"` (so it owns the pre-accounts data), logs in with `APP_PASSWORD` (no stored hash; `SESSION_SECRET` is then required) and can list, reset and delete accounts (`app/api/routes_admin.py`; deletion removes checkpoints and store items, then calls each feature's `delete_user_data`, e.g. chunks and `uploads/<user_id>/`). `scripts.claim_anonymous_data` moves data of old `anon-*` users to the admin. The account's name and username reach the agents as `AgentContext.user` (`USER_SECTION`). Everything else — DB rows, vector search filter `{"user_id": {"$eq": ...}}`, memory namespace, upload dir — is keyed by `user_id`. Preserve this scoping in any new query or tool.

**SQL safety:** the SQL agent connects with `READONLY_DATABASE_URL` as `agent_readonly` (created in `db/init/03_readonly_role.sql`, extended in `04_market_schema.sql`: SELECT-only on `market`, read-only transactions, 10s timeout, no access to app tables). `execute_readonly` additionally rejects anything that isn't a single `SELECT`/`WITH` and caps rows at `SQL_MAX_ROWS`. The prompt shows schema-qualified table names. To target another database, change `READONLY_DATABASE_URL` and `SCHEMAS` in `app/agents/sql/tools.py` (`get_readonly_engine` is in `app/core/db.py`).

**Stock data (`app/features/market/`):** `scripts.load_stocks` → `load_market()` re-applies the idempotent `db/init/04_market_schema.sql` (so existing DBs get the schema and grants), inserts placeholder `stocks` rows, refreshes profiles from `yf.Ticker(t).info` (one request per ticker, retried), then `yf.download` in batches of 50 and upserts `daily_prices` via COPY into a temp table (setting `updated_at`; `/api/market/status` reports the newest price/profile `updated_at` as "last updated" in the Readme). Incremental by default: starts `OVERLAP_DAYS` before `max(trade_date)`. It writes as the owner (`DATABASE_URL`) and can run while the app is up. yfinance's `dividendYield` is already a percentage.

**Daily update (`app/features/market/scheduler.py`):** the market feature's `start` hook starts `run_daily()` as an asyncio task when `MARKET_UPDATE_TIME` is set (cancelled on shutdown via the exit stack). It catches up once at startup if `max(trade_date)` is older than `latest_session()`, then sleeps until `next_run()` (weekdays, `America/New_York`; needs `tzdata` on Windows). `run_update()` runs `load_market` in a thread under `update_lock()` (a Postgres advisory lock also taken by `scripts.load_stocks`, so multiple workers or a manual run never overlap). Profiles are refreshed only when older than 7 days. Failures are logged and retried 3 times, 15 min apart; the task never dies. There's no holiday calendar: on a holiday the run just upserts nothing.

## Adding an agent or workflow

1. Create `app/agents/<name>/` with `tools.py` (tools read per-user data via `ToolRuntime[AgentContext]`; keep the `user_id` scoping), `prompts.py` (system prompt ending with `LANGUAGE_RULE` and `MEMORY_RULE`, plus a one-line `ROUTE_DESCRIPTION`) and `agent.py` (`build_agent(name="<name>_agent", ...)` and a `SPEC`).
2. Append the `SPEC` to `AGENTS` in `app/agents/registry.py`.
3. Add routing tests in `tests/test_router.py` (its hints route to it, the model prompt lists it).

No router, API, UI or `main.py` changes are needed. If the agent needs its own data (tables, ingestion, routes, background jobs, per-user cleanup), add a feature in `app/features/<name>/` with a `Feature` (`features/base.py`) appended to `features/registry.py`, and put its tables in `app/core/db.py`.

A multi-step workflow (e.g. researcher → report writer) is one entry: `build` returns a `StateGraph` with `messages` in its state (plus its own keys, e.g. findings), each step a `build_agent(...)`, compiled with `name=`; list every inner agent name in `message_names`. `_to_events` streams tokens of every inner `model` node, so filter by `namespace` if only the last step should stream.

## Notes

- Config is `pydantic-settings` reading `.env` (`app/core/config.py`, cached via `get_settings()`); `.env.example` documents every variable. SQLAlchemy URLs get the `postgresql+psycopg://` prefix via `sqlalchemy_url` properties, while psycopg/LangGraph use the raw `DATABASE_URL`.
- Sync DB/vector work is wrapped in `asyncio.to_thread` from async routes and tools.
- Every DB connection must survive a Postgres restart (WSL stops Postgres when the distro shuts down): SQLAlchemy engines (including PGVector's, via `engine_args`) use `pool_pre_ping=True`, and the LangGraph pool uses `check=AsyncConnectionPool.check_connection` plus TCP keepalives. Don't go back to `from_conn_string`, which holds one connection that never reconnects.
- Deployment: Google Cloud Run (project `smallie-review`, region `asia-southeast1`, https://smallie-976519788978.asia-southeast1.run.app) + Neon Postgres 18 (Singapore). Steps are in README "Deploying".
  - `Dockerfile`: python:3.12-slim + uv, non-root `user` (the app dir is created and chowned before `USER`, otherwise `uv sync` can't create `.venv`), listens on `$PORT`, no `--loop` flag (Linux).
  - Built by Cloud Build via `--source .` (the image lands in Artifact Registry `asia-southeast1-docker.pkg.dev/smallie-review/cloud-run-source-deploy/smallie`; Neon holds only the database); `.gcloudignore`/`.dockerignore` keep `.env`, `.venv`, `uploads`, tests and `cloudrun.env.yaml` out. The default compute service account needs `roles/run.builder`.
  - Config comes from `cloudrun.env.yaml` (gitignored, holds secrets: `.env` values + Neon URLs + `SESSION_HTTPS_ONLY=true`), not `.env`.
  - `--no-cpu-throttling` is required: document ingestion, `save_turn` and the market scheduler run after the response is sent. `--max-instances 1` caps cost. The container disk is ephemeral, which is fine because uploads are only read during ingestion.
  - Neon: use the direct (non `-pooler`) URL, because of the advisory locks. `agent_readonly` was created by hand with a strong password (Neon rejects `'readonly'`); the DB is `smalliedb`. The first stock load was run from the PC (`DATABASE_URL=<neon> load_stocks --full`).
- `*.sh` files must keep LF line endings (they run in WSL).
- Default models are OpenRouter free tier (~20 req/min, low daily cap); one question takes 2–5 model calls plus at most 1 router call (research: up to `RESEARCH_MAX_MODEL_CALLS` + 1–2 for the writer).
